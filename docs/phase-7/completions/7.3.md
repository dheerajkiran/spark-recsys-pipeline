# Checkpoint 7.3 — identity, project isolation, and credentials

Status: complete locally, November 11, 2026. Branch: `phase7-identity`, based on `main` at `2ed3d9a` (PR #15). This record accompanies the checkpoint implementation commit on that branch; see Git history for its identity. No PR, merge, Cognito pool, cloud table, or AWS deployment is claimed.

## Implemented behavior

The shared asynchronous API verifies dashboard access JWTs and current developer-key state before resolving project permissions. Project creation/list/read and key issue/list/revoke now work locally. Authorization for all 23 project-scoped OpenAPI operations is enforced before child-resource handling. Future data/ML endpoints return a controlled `503` after permission and input checks. Public demo sessions remain disabled.

| Area | Observed implementation |
|---|---|
| Dashboard identity | RS256 signature, configured issuer/JWKS, client identity, optional resource audience, token use, expiry/issuance/not-before, human username, and required scopes; principal is `issuer#sub` |
| Local setup | Explicit local RSA trust, private operator initialization/token/membership tool, one-hour test tokens, and rejection of local trust in Lambda |
| Project access | Owner/viewer membership; verified outsiders receive `404`, insufficient member/integration permissions `403`, invalid credentials `401` |
| Developer credentials | Random identifier plus 32 random secret bytes, SHA-256 digest and timing-safe verification, project/scopes, at-most-30-day expiry, one-time disclosure, immediate next-request revocation |
| Mutations | Actor/operation/project/payload-bound seven-day idempotency; concurrent retries create one resource; issuance replay returns `secret: null` |
| Persistence | Private atomic local snapshots with cross-process writer lock; strongly consistent DynamoDB partition reads and conditional all-or-none transactions |
| Lists | Bounded response pages and encrypted/authenticated actor/route/project/snapshot cursors expiring after 15 minutes; same-clock inserts do not enter an earlier snapshot |
| Audit and errors | Hashed actors, safe action/resource/request metadata, no persisted plaintext key secrets or bearer tokens, contract-required error details, `Cache-Control: no-store` |
| HTTP boundary | Async transport parity, bounded streaming/base64 bodies, malformed target/header handling, sanitized adapter failures |

## Limitations and next dependency

Cognito JWKS verification is covered with signed tokens and a stubbed key endpoint, not a deployed user pool. Owner-controlled user-pool provisioning, disabled self-sign-up, hosted login/PKCE, IAM, cloud service behavior, and account preflight remain 7.10–7.11 work. JWT verification does not query Cognito revocation state; previously issued access tokens can remain valid until expiry. Developer-key revocation is checked separately on every request; requests already authorized before revocation may finish.

The filesystem identity store is separate from 7.2's workflow runner and does not establish durable distributed job/outbox semantics. A crashed local writer leaves a lock for explicit operator recovery. Lists materialize authorized partition results before slicing pages, so response limits do not establish bounded database work for large accounts. Old replay/audit record cleanup is not provisioned. Dataset/event ingestion and actual colliding customer-item storage are not implemented merely because their authorization gates pass.

Original research code and historical result artifacts were unchanged. Full Spark pipeline/benchmarks and the unchanged CPU image were not rerun. The temporary API server was stopped and the DynamoDB Local container removed after verification. No training workflow, AWS resource, or credit-funded service usage occurred. The next checkpoint is **7.4: upload validation, ingestion, and durable job records**.
